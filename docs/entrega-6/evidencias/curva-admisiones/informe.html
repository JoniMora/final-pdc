Admisiones de reservas con 1, 2 y 4 APIs

Tres corridas por configuracion; 100 POST por corrida, 64 conexiones maximas, cuatro workers constantes. Media y desvio muestral. Sin reintentos.

El tiempo del cliente incluye espera por conexion. El p95 de cada corrida no mezcla consultas de drenaje. La barra muestra media de esos p95, no el percentil de todas las corridas juntas.

Cada API agrupa sus admisiones en lotes de hasta 50 por commit, y cada commit espera la confirmacion semisincrona de la replica. El agrupamiento es por proceso: con la misma carga repartida entre mas instancias, cada una forma lotes mas chicos y el primario paga mas commits durables. Por eso agregar APIs no aumenta las admisiones por segundo: el cuello de botella es el commit del primario, no la CPU de la API.

La prueba caliente de 500 solicitudes se conserva por separado. Esta curva usa 100 por corrida; no debe presentarse como nueve rafagas de 500. Las APIs comparten primario, disco y Redis; no se exige ni se presupone mejora lineal.
